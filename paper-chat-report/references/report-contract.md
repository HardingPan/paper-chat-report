# Paper Chat Report Contract

这个文件定义 `paper-chat-report` 的默认成稿结构和边界。

## 成稿目标

最终结果应该是一份可以单独阅读的论文报告，而不是：

- 聊天记录清洗稿
- 逐轮问答整理稿
- 逐段翻译
- 只列亮点和结论的简化摘要

读完报告后，一个没看过论文和原对话的人，至少应该知道：

- 论文到底想解决什么问题
- 这个问题为什么难
- 方法是如何拆阶段、拆模块、拆约束的
- 关键公式在流程里分别负责什么
- 哪些实验最能支撑作者 claim
- 论文的边界和局限是什么

## 来源优先级

这个 skill 默认采用双源策略：

- 对话导出：解释材料来源
- 原论文：事实纠偏来源

因此：

- 可以吸收对话里讲得好的解释方式
- 但不能把对话里不准确的内容当真
- 一旦和原文冲突，回到原文

## 默认结构

```md
# 论文标题

> 三句话总结

## 0. 阅读入口

## 1. 基本信息

## 2. 研究问题与核心困难

### 2.1 问题背景

### 2.2 研究现状与局限（相关工作）

### 2.3 核心研究问题

## 3. 核心贡献

## 4. 整体主线

## 5. 方法总览与系统分解

## 6. 方法详解

### 6.1 问题形式化/建模

### 6.2 关键模块设计

### 6.3 训练/学习过程

### 6.4 推理/部署过程

## 7. 图表与实验解读

## 8. 局限与边界

## 9. 结论

## 10. 参考链接
```

## 硬约束

- 报告必须是 standalone 文档
- 不能出现 `You said`、`ChatGPT said`、`Claude said`、`Gemini said`
- 不能出现"你回复继续我再继续"之类对话残留
- 中文为主，英文术语保留
- 方法解释优先，公式要嵌入方法小节

## 公式规则

**禁止单独设置"公式汇总表"或"公式速查"章节。**

公式必须：
- 在**首次出现的上下文**中完整定义
- 紧跟解释：每项是什么、为什么需要它、没有它会怎样

推荐格式：
- inline math：`$z_t$`
- block math：

```latex
\mathcal{L} = \lambda_1 \mathcal{L}_{main} + \lambda_2 \mathcal{L}_{aux}
```

如果论文公式较多，可在「基本信息」后加一个极简的「符号说明」：

| 符号 | 含义 |
|------|------|
| $z_t$ | 潜在状态 |
| $f_\theta$ | 动力学模型 |

但**只列符号，不重复公式**。

## 图片标注规则

**禁止在文末设置"建议插图"章节。**

图片引用应在正文的**合适位置**用语义标记标注：

```markdown
[[FIG:4|学习曲线对比：SimDist vs RL baselines，突出15-30分钟数据点的性能差距]]

[[TAB:2|消融实验：数据规模对性能的影响]]
```

标记规范：
- `FIG:n` 表示论文第 n 个图
- `TAB:n` 表示论文第 n 个表
- `|` 后是描述性文字，说明这张图/表的核心内容和强调重点

渲染后效果（平台自适应）：
- 语雀：`<span style="color:#ff6b6b">[插入图4：...]</span>`
- 标准 Markdown：`🔴 **[插入图4：...]**`
- Notion：Callout block

## 方法部分要求

如果论文方法具有明显流程性、阶段性或优化结构，则方法部分至少要回答：

- 输入是什么
- 固定量是什么
- 优化变量 / 推断对象是什么
- 每一步的核心操作是什么
- 输出怎样流向下一阶段
- 关键公式分别压制什么误差来源

## Markdown 组织要求

- `blockquote` 用于核心 insight
- `table` 用于模块分工、机制速查、实验对照
- fenced `latex` block 用于关键公式
- 普通列表用于贡献、结论

## 写作提醒

- 对话里的优质解释可以保留其逻辑，但要重写成书面报告
- 不能让 transcript 结构决定最终文章结构
- 如果对话已经把方法讲开了，最终报告应进一步压实为"主线 + 机制 + 证据"
- 如果对话只覆盖了部分章节，剩余部分必须由原文补足或明确标注信息不足

## 相关工作定位

相关工作不再作为独立章节（原第 9 节），而是整合到：

**2.2 研究现状与局限** —— 从"问题驱动"视角回顾：
- 前人做了什么
- 这些方法的核心局限是什么
- 为什么这些局限导致它们无法解决本文的问题

这样的安排让相关工作服务于"问题的引入"，而非孤立罗列。
